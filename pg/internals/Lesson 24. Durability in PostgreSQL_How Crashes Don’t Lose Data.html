🔒 Durability in PostgreSQL: Why Crashes Don’t Lose Data

Durability means that once a transaction commits, its changes are safe even if the server crashes immediately afterward.

Durability is the D in ACID.
PostgreSQL ensures that once a transaction commits (assuming fsync = true and synchronous_commit=on), its changes cannot be lost, even in the event of a crash, power failure, or restart.

Let’s see how PostgreSQL achieves this.

💽 The Role of WAL (Write-Ahead Log)

In PostgreSQL, all changes first occur in shared memory pages (the shared buffer cache). Because memory is volatile, PostgreSQL must persist these changes safely to disk. That’s where Write-Ahead Logging (WAL) comes in:

  • Each data change is recorded in the WAL buffer in memory.

  • The WAL buffer is flushed to disk (WAL files) before the COMMIT completes.

  • Only after the WAL is safely written does PostgreSQL confirm the commit.

✅ During crash recovery, PostgreSQL replays WAL records to restore all committed changes that weren’t yet written to data files.

🧠 Atomic Changes Within Pages

In MySQL, mini-transactions (MTRs) ensure page modifications are atomic, so each page update is either fully applied or fully undone.

PostgreSQL achieves page-level atomicity differently from MTRs. It combines critical sections, WAL logging, and full-page writes to ensure each page modification is either fully applied or fully recoverable after a crash.

Analogy:
Think of a to-do list:

  1. Write down all the steps.

  2. Perform them one by one.

  3. Mark ✅ at the end when everything is done.

If a crash occurs midway:

  • ✅ present → the work is complete.

  • ✅ missing → redo or discard.

Similarly, PostgreSQL logs all steps in WAL. Only after the commit record is written does the transaction become truly durable.

⚙️ Why Atomicity Matters

A single page modification in PostgreSQL involves multiple in-memory operations:

  1. Modify tuples or page headers.

  2. Mark the buffer as dirty.

  3. Write corresponding WAL entries.

If a crash occurs mid-way, a page could be partially modified, risking corruption. PostgreSQL uses critical sections to reduce the risk of mid-operation errors during page modifications.

Inside a critical section:

  • Errors and interrupts are temporarily disabled.

  • If a crash occurs, WAL replay safely restores the page to a consistent state.

🧩 How Critical Sections Work

A critical section (START_CRIT_SECTION() … END_CRIT_SECTION()) temporarily disables errors and interrupts.

This ensures that, during page modifications, software-level interruptions such as errors or signals cannot abort the operation midway.

Effectively, the modification becomes logically atomic: either it completes and is eventually made durable via WAL, or the system crashes before the critical section ends, in which case WAL replay restores the page safely.

🛡️ Preventing Partial Page Writes

Even with logical atomicity, physical risks remain: what if power fails during a disk write? This can create a torn page (half old, half new data).

MySQL (InnoDB) handles this with a doublewrite buffer, but PostgreSQL uses a different approach.

🧱 Torn Page / Partial Write Handling

PostgreSQL doesn’t use a doublewrite buffer. Instead, it relies on full-page writes in WAL:

  • When a page is modified for the first time after a checkpoint, the entire page image is logged in WAL.

  • On crash recovery, this image fully restores the page.

  • To minimize overhead, full-page writes occur only when necessary.

🧰 PostgreSQL Protection Mechanisms — Summary

  1. WAL ensures all changes are logged before reaching the data file.

  2. Critical sections prevent software-level interruptions during page modifications.

  3. Checksums detect page corruption (if enabled).

  4. Full-page writes capture the complete page image when needed.

  5. During recovery, WAL replay rebuilds any partially written or damaged pages.

🔐 Together, these mechanisms prevent torn pages, corruption, and data loss, ensuring PostgreSQL’s durability and consistency.

📊 PostgreSQL vs MySQL — Durability Design

Feature MySQL (InnoDB) PostgreSQL
In-memory atomicity Mini-transaction (MTR) Page-level atomicity (MIR)
Logging Redo log WAL
Crash recovery Redo replay + doublewrite buffer WAL replay + full-page writes
Torn page protection Doublewrite buffer Full-page WAL images
Write ordering Redo flush before page flush WAL flush before page flush

🔁 Crash Recovery Internals

After a crash, PostgreSQL automatically performs recovery using the WAL.

🔄 Recovery Overview

Postmaster → Startup Process → WAL → Buffer Manager → Checkpoint

PostgreSQL replays WAL records sequentially from the last checkpoint, applying all operations until the system becomes consistent again.

🌐 Durability in Replication

WAL also powers PostgreSQL replication:

  • WAL records are streamed to replicas in real time.

  • Replicas apply the changes as they arrive.

  • If the primary crashes, properly configured replicas already contain all committed data.

This extends durability beyond a single node, ensuring data safety across servers.

📌 Key Takeaways

  • 🧱 WAL is the foundation of PostgreSQL’s durability.

  • 🧩 Critical sections reduce the risk of software-level interruptions during in-memory page modifications, helping updates remain logically atomic.

  • 🛡️ Full-page writes and checksums protect against torn pages.

  • 🔁 Crash recovery replays WAL to restore committed data.

  • 🌐 Replication extends durability across servers.

💡 PostgreSQL’s durability is a layered design combining buffers, WAL, checksums, and recovery, ensuring your data survives any crash every time.
