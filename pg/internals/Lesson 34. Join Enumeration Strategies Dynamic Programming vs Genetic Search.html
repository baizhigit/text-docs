⚔️ Join Enumeration Strategies: Dynamic Programming vs Genetic Search

Dive into how PostgreSQL explore the space of join orders, comparing the classic Dynamic Programming approach with Genetic Algorithms, and understand the trade-offs in query optimization.

This lesson explains how PostgreSQL explores join orders in queries involving many tables. We will compare two main approaches: Dynamic Programming and Genetic Search. Before diving into the details, let’s look at an example.

⚡ 1. Example: Complex Join with Multiple Tables

Here is a query that joins 16 tables. We use it to observe how different planning algorithms perform.

EXPLAIN ANALYZE
SELECT 
    c.custkey,
    c.name,
    n.name AS nation,
    r.name AS region,
    o.orderkey,
    o.orderdate,
    l.partkey,
    p.name AS part_name,
    pc.name AS category,
    s.name AS supplier_name,
    sh.ship_date,
    car.name AS carrier,
    w.location AS warehouse,
    d.name AS dept,
    e.name AS employee,
    pr.discount,
    tx.amount
FROM customers c
JOIN orders o           ON c.custkey = o.custkey
JOIN lineitems l        ON o.orderkey = l.orderkey
JOIN parts p            ON l.partkey = p.partkey
JOIN part_categories pc ON p.category_id = pc.category_id
JOIN suppliers s        ON l.suppkey = s.suppkey
JOIN shipments sh       ON l.ship_id = sh.ship_id
JOIN carriers car       ON sh.carrier_id = car.carrier_id
JOIN warehouses w       ON l.warehouse_id = w.warehouse_id
JOIN nation n           ON c.nationkey = n.nationkey
JOIN region r           ON n.regionkey = r.regionkey
JOIN accounts a         ON c.custkey = a.custkey
JOIN transactions tx    ON a.account_id = tx.account_id
JOIN promotions pr      ON p.partkey = pr.partkey
JOIN employees e        ON e.emp_id = (l.lineitem_id % 5000) + 1
JOIN departments d      ON e.dept_id = d.dept_id
WHERE r.name = 'ASIA'
  AND p.type = 'STEEL'
  AND o.orderdate BETWEEN DATE '2024-01-01' AND DATE '2024-12-31';

Test Results

Method Default DP without splitting GA without splitting lightweight GA without splitting
Total Cost 33170.13 23124.31 23345.53 23892.67
Planning Time (ms) 3.303 103.222 32.575 2.771
Execution Time (ms) 358.663 75.848 82.125 84.029

Here we divide the SQL processing time into Planning Time and Execution Time.

The table above clearly shows that PostgreSQL’s default settings perform poorly for this complex join. By default, PostgreSQL uses join_collapse_limit = 8 and geqo_threshold = 12. With these settings, a 16-table join is split into smaller sub-joins, each optimized using dynamic programming (DP). In our test, planning was very fast at just 3.3 ms, but execution was much slower at 358.663 ms.

When we increased join_collapse_limit and geqo_threshold both to 32, PostgreSQL applied DP to all 16 tables without splitting. Planning time increased to 103.222 ms, but execution time dropped sharply to 75.848 ms. This demonstrates that DP without splitting takes longer to plan but generates a much more efficient join order. The estimated costs also decreased, as expected.

Next, we set geqo_threshold = 8 to force the use of the genetic algorithm (GEQO). Planning time was 32.575 ms, and execution took 82.125 ms. The estimated cost was slightly higher than DP without splitting.

Finally, by further tuning GEQO with geqo_pool_size = 10 and geqo_effort = 1, planning time dropped to 2.77 ms, with only a slight increase in execution time. This configuration achieved the best overall performance despite not having the lowest cost, outperforming the default settings in both planning and execution.

Key Takeaways:

  1. Default settings are not always optimal for complex queries.

  2. Complex joins often require careful tuning to achieve the best performance.

  3. Knowing when and how to use Dynamic Programming versus the Genetic Algorithm is crucial for effectively optimizing complex join queries.

🧐 2. Why Join Enumeration Matters

When a query involves multiple tables, the order in which joins are executed has a major impact on performance.

  • Join enumeration is the process of exploring all possible join sequences to find the most efficient plan.

  • Databases aim to minimize execution cost while keeping computation manageable.

This lesson covers two main strategies:

  1. Dynamic Programming – traditional, widely used, and deterministic.

  2. Genetic Search – modern, heuristic, approximate, and inspired by evolution.

Below is a simple illustration of how PostgreSQL applies these two strategies (the real process is more complex):

The process after splitting a large join can be quite complex. For example, if join_collapse_limit = 10 and geqo_threshold = 8, a 16-table join is split into two groups: 10 tables and 6 tables. The first 10 tables are processed using the Genetic Query Optimization (GEQO) algorithm to produce an intermediate result. This result is then joined with the remaining 6 tables. Since 1 + 6 < 8, the final join is handled using Dynamic Programming.

It’s important to note that the default parameters do not fully leverage GEQO. For complex joins, understanding how to use GEQO effectively can significantly improve performance.

This lesson focuses on DP and GA without using splitting.

🌲 3. Dynamic Programming for Join Enumeration

3.1 Concept

Dynamic Programming builds join trees from the bottom up:

  1. Start with the base tables.

  2. Combine pairs of tables to form simple 2-way joins.

  3. Step by step, combine small joins into larger joins.

  4. The planner usually keeps the lowest-cost plan for each set of tables, but it may also retain additional candidates that could lead to better overall plans.

PostgreSQL’s dynamic programming (DP) approach is inspired by academic research, but it is not a pure DP algorithm. It uses aggressive pruning to shrink the search space early, discarding many join combinations before fully exploring them. As a result, the chosen plan is not guaranteed to be optimal, but in practice the chance of missing the best plan is very small.

To handle queries involving a very large number of tables, PostgreSQL also uses join splitting, which breaks a large join into smaller groups. This significantly reduces the search space and helps PostgreSQL generate plans that perform reasonably well.

Pruning and splitting are both crucial when the join search space grows too large to handle.

3.2 Advantages

  • Deterministic but not always optimal: Even with pruning, the search may not always find the best plan, but in practice PostgreSQL almost always chooses the best plan when the statistics are reliable.

  • No repeated work: Paths that have already been computed are reused, avoiding unnecessary recalculation.

  • Effective pruning: Retains most of the promising join combinations while shrinking the search space significantly.

3.3 Limitations

  • Rapid growth: Planning becomes expensive as the number of tables increases.

  • High memory usage: Many intermediate join combinations must be stored.

  • Not practical for very large joins: Without splitting, the DP approach struggles with extremely large multi-table queries.

Key Takeaways

  1. The planner calls search (make_one_rel()) to identify all possible access paths for the query.

  2. Search builds level-1 access paths and then hands control to DP (standard_join_search()).

  3. DP processes joins level by level (from 2-way joins up to N-way joins):

    • Level function (join_search_one_level()) constructs joinrels of the current size.

      • First, it considers left-sided and right-sided plans.

        • For each pair, it checks whether join clauses or join restrictions exist:

          • If join clauses or join restrictions exist:

            • Calls make_rels_by_clause_joins.

            • make_join_rel() creates join paths.

            • populate_joinrel_with_paths() returns candidate paths.

          • Otherwise:

            • Calls make_rels_by_clauseless_joins.

      • Bushy joins are considered when join clauses or join order restrictions allow.

  4. DP calls set_cheapest() to select the cheapest paths at each level.

🧬 4. Genetic Search for Join Enumeration

4.1 Why GEQO Exists

PostgreSQL’s traditional join optimizer uses dynamic programming (DP) with pruning. It enumerates all join orders that DP considers promising and chooses the cheapest based on estimated execution cost. However, the number of possible join orders grows rapidly, and for queries with many tables, fully enumerating all options becomes prohibitively expensive.

To address this, PostgreSQL introduces GEQO (Genetic Query Optimizer), which uses a heuristic search:

  • Trades some accuracy for significantly greater speed

  • Finds “good enough” join orders without exploring the entire search space

  • Applies concepts from genetic algorithms (GAs)

4.2 Concept

Genetic Algorithms are heuristic and probabilistic:

  1. Represent join orders as chromosomes (table sequences).

  2. Generate an initial population of random join orders.

  3. Evaluate fitness based on estimated execution cost.

  4. Apply crossover and mutation to produce new generations.

  5. Repeat until a “good enough” solution is found.

4.3 Advantages

  • Efficiently handles very large join queries.

  • Explores a variety of plans without evaluating every possibility.

  • Quickly finds near-optimal solutions when dynamic programming is too expensive.

4.4 Limitations

  • Non-deterministic: Different runs may produce different plans.

  • Requires tuning: Population size, mutation rate, and number of generations influence the results.

Analogy:
GA is like evolution: survival of the fittest join orders, gradually improving over generations.

Key Takeaways

  1. Planner starts by invoking GEQO (geqo()).

  2. GEQO starts by generating a population of random table sequences, referred to as tours.

  3. Each individual in the population is evaluated (geqo_eval()) to compute its cost (fitness), and the results are stored in Pool.

  4. The population is ranked by fitness, with lower-cost tours preferred.

  5. The GEQO evolution loop iteratively improves the population:

    • Sel (geqo_selection()) selects parent tours with biased selection.

    • Edge (gimme_edge_table()) builds edge tables from the parents.

    • Recomb (gimme_tour()) generates new child tours via edge recombination.

    • Eval evaluates each child’s cost; the child replaces the weakest individual in Pool.

  6. After the evolution loop, Best selects the best tour, and GEQO returns a new join relation to Planner, whose cheapest path corresponds to the best plan from that tour.

Using population-based evolution, fitness evaluation, recombination, and selection, GEQO efficiently finds good join plans for queries with many tables.

🔍 5. Comparing DP and GA

Aspect Dynamic Programming (DP) Genetic Algorithm (GA)
Optimality Theoretically guaranteed with accurate statistics Near-optimal, probabilistic
Performance Fast for small tables, can be slow for many tables Handles large numbers of tables efficiently
Memory Usage High (stores planner information for many table combinations) Moderate (stores only population of tours)
Determinism Deterministic Non-deterministic
Practical Use Cases Small to medium joins in most RDBMS Very large queries or experimental optimization

🔑 6. Summary

  • Join enumeration is critical for optimizing multi-table queries.

  • Dynamic Programming (DP): deterministic; aims to find the optimal join order but can be computationally expensive.

  • Genetic Algorithm (GA): heuristic and non-deterministic; efficiently finds near-optimal plans for large joins.

  • Both strategies rely on cost estimates, so accurate statistics are essential for good performance.

  • Developers can influence results through query design, indexing, and keeping statistics up to date.

  • Users can leverage our trace tool to analyze the detailed planning process of complex joins.
