⚙️ How PostgreSQL Ensures Atomicity Using MVCC, CLOG, and WAL

Atomicity means all-or-nothing, and PostgreSQL takes this seriously.

📌 What Is Atomicity?

In databases, atomicity ensures that a transaction is treated as a single, indivisible unit of work. Either all operations succeed, or none are applied.

Example:

BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;

In PostgreSQL, if anything goes wrong, whether an error occurs or the system crashes, none of the changes are applied. PostgreSQL ensures atomicity through MVCC, CLOG, and WAL, while heap tuples store the actual data versions tracked by MVCC.

🔄 PostgreSQL Atomicity: From Transactions to Crash Recovery

🔹 1. Transaction boundaries

  • A transaction is all-or-nothing: either all changes are visible after COMMIT, or none after ROLLBACK.

  • Subtransactions extend this guarantee to block-level error recovery (savepoints).

🔹 2. Atomic catalog updates

  • Transactional DDL changes (e.g., CREATE TABLE, ALTER TABLE) are also atomic because catalog modifications are transactional. If a crash happens, half-created objects don’t survive.

🔹 3. WAL + Commit Protocol

  • Changes are written to the WAL before being applied to data files (write-ahead).

  • XLogFlush() at commit ensures WAL for this transaction reaches disk before acknowledging success.

  • This guarantees atomic durability: either WAL is replayed (transaction committed) or ignored (transaction aborted).

🔹 4. Atomic visibility via MVCC

  • A tuple is never partially visible.

  • New versions are linked in, but only committed ones become visible to other transactions.

  • Old versions remain accessible until cleanup.

🔹 5. Error handling & subtransactions

  • If an error occurs mid-transaction, all changes are rolled back to the last savepoint (or the entire transaction).

  • This prevents partial state leaks.

🔹 6. Crash recovery guarantees

  • After a crash, PostgreSQL replays WAL in two phases:

    • REDO for committed transactions.

    • Ignore for aborted or incomplete ones.

  • This ensures no transaction is half-applied.

🔹 7. Edge cases worth noting

  • Transactional DDL + DML mix: both obey atomicity.

  • Two-phase commit (2PC): atomicity extends across nodes with PREPARE TRANSACTION + COMMIT PREPARED.

  • Replication: WAL streaming ensures the same atomicity guarantees on standby servers.

👉 In short: PostgreSQL’s atomicity isn’t just about “transactions roll back on error”; it’s carefully enforced across catalogs, WAL, visibility rules, and even distributed transactions.

🧠 MVCC: Multi-Version Concurrency Control

PostgreSQL uses MVCC to manage concurrent transactions:

  • Each row version (tuple) has:

    • t_xmin = the XID of the inserting transaction

    • t_xmax = the XID that either deleted, updated (replaced), or holds a lock on the row

  • Updates create new versions; deletes mark the old version as logically dead (MVCC handles visibility).

  • This design allows PostgreSQL to track which rows are visible to which transactions.

🔁 CLOG: Tracking Commit Status

CLOG (Commit Log) stores the status of every transaction:

  • Each XID has a few bits representing its state:

    • in-progress

    • committed

    • aborted

    • subcommitted

  • Heap tuples only store t_xmin/t_xmax.

  • The actual commit status is read from CLOG for visibility checks.

Example:

  1. Transaction 5326 inserts a row → t_xmin = 5326

  2. Transaction rolls back → CLOG marks 5326 as aborted

  3. Any SELECT ignores the tuple automatically

Think of CLOG as a scoreboard: tuples reference the ticket number (XID), and CLOG tells you if it won (committed) or lost (aborted).

🔐 WAL: Ensuring Crash Safety

Even if CLOG pages are in memory and not yet flushed:

  • WAL (Write-Ahead Log) guarantees durability.

  • When a transaction commits:

    1. PostgreSQL writes a commit record to WAL.

    2. WAL is flushed to disk before returning COMMIT to the client.

      Note: Unless stated otherwise, we assume fsync=on and synchronous_commit=on.

  • If the server crashes:

    • WAL is replayed during recovery.

    • CLOG and heap tuples are updated accordingly.

Key principle: CLOG is a performance cache; WAL is the source of truth.

🛠️ Example: Transaction Lifecycle

begin;
update sbtest1 set k = k + 1 where id = 1;
delete from sbtest1 where id = 2;
rollback;

Internally:

  1. A new tuple is created with your XID (xmin = your transaction).

  2. ROLLBACK marks your XID as aborted in CLOG.

  3. Tuples become invisible immediately.

  4. VACUUM later removes them physically.

Notice: rollback doesn’t touch old data; it’s almost instantaneous regardless of row count.

If the server crashes:

  1. PostgreSQL reads WAL.

  2. Replays committed transactions:

  • Updates heap tuples

  • Updates CLOG entries to committed

  1. Aborted transactions remain invisible.

✅ This ensures both atomicity and durability.

⚖️ Atomicity Differences: PostgreSQL vs MySQL

PostgreSQL and MySQL (InnoDB) differ in the way they enforce transaction atomicity.

1️⃣ Level of Atomicity

Feature PostgreSQL MySQL (InnoDB)
Transaction atomicity (DML) ✅ Full transaction level ✅ Full transaction level
Transaction atomicity (DDL) ✅ Most DDL is transactional ❌ DDL is auto-committed
Error handling ❌ Any statement failure aborts the entire transaction ❌ Most DML statement errors roll back only the statement; some critical errors abort the entire transaction.
Coverage DML + transactional DDL DML only; DDL auto-committed

💡Example:

✅ PostgreSQL:

BEGIN;
INSERT INTO tx VALUES (1);
INSERT INTO tx VALUES (1);  -- Duplicate key error
COMMIT;  -- Entire transaction is rolled back, first insert undone

❌ MySQL / InnoDB:

BEGIN;
INSERT INTO tx VALUES (1);
INSERT INTO tx VALUES (1);  -- Duplicate key error
COMMIT;  -- Failed statement rolled back, first insert remains

2️⃣Error Detection Timing and Location

  • PostgreSQL:

    • Errors like duplicate keys are detected during index insert operations.

    • Heap may already contain the row, but the transaction is marked aborted.

    • MVCC + WAL ensures the aborted row is invisible to other transactions; space is later reclaimed by VACUUM.

  • MySQL / InnoDB:

    • Error detection prevents data from being inserted into the clustered index.

    • Failed statements never modify table data.

3️⃣ Transactional DDL

  • PostgreSQL:

    • Most DDL is transactional, allowing rollback.

    • DML and most DDL statements can run together in one transaction, guaranteeing full atomicity.

  • MySQL:

    • DDL is auto-committed and cannot be rolled back.

    • Mixing DDL and DML does not guarantee atomicity.

4️⃣ Why the Difference Exists

  1. PostgreSQL uses a unified transaction model, where DML and transactional DDL update system catalogs under MVCC.

  2. MySQL’s multi-storage engine architecture limits transactional support.

  3. PostgreSQL leverages WAL + CLOG + MVCC to ensure efficient, safe rollback.

✅ Key Takeaways

  • PostgreSQL rollback is fast due to MVCC and CLOG.

  • CLOG tracks transaction status efficiently; WAL guarantees crash safety.

  • Old tuples are never overwritten; aborted tuples are ignored and cleaned later by VACUUM.

  • This architecture allows PostgreSQL to support transactional DDL, fast rollbacks, and full ACID compliance.
