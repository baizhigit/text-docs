📚 Inside PostgreSQL’s Planner: From Query to Logical Plan

Learn how PostgreSQL transforms SQL into a logical plan, why it explores multiple alternatives, and how paths and costs guide the selection of the final executable plan.

📊 1. How COUNT(*) Behaves Differently in MySQL and PostgreSQL

⚖️ 1.1 Comparing Execution Plans

When migrating from MySQL to PostgreSQL, users often wonder how the planner differs. Let’s start with a simple example showing how COUNT(*) runs on a large orders table in MySQL.

mysql> explain select count(*) from orders;
+----+-------------+--------+------------+-------+---------------+---------------------+---------+------+--------+----------+-------------+
| id | select_type | table  | partitions | type  | possible_keys | key                 | key_len | ref  | rows   | filtered | Extra       |
+----+-------------+--------+------------+-------+---------------+---------------------+---------+------+--------+----------+-------------+
|  1 | SIMPLE      | orders | NULL       | index | NULL          | idx_orders_customer | 4       | NULL | 998490 |   100.00 | Using index |
+----+-------------+--------+------------+-------+---------------+---------------------+---------+------+--------+----------+-------------+
1 row in set, 1 warning (0.00 sec)

  • MySQL efficiently uses the idx_orders_customer index to compute COUNT(*).

  • Because the index occupies relatively few pages, scanning it is faster than reading the entire table.

Now, let’s examine how PostgreSQL executes this query:

# SET max_parallel_workers_per_gather = 0;
SET
# explain select count(*) from orders;
                              QUERY PLAN
----------------------------------------------------------------------
 Aggregate  (cost=17906.00..17906.01 rows=1 width=8)
   ->  Seq Scan on orders  (cost=0.00..15406.00 rows=1000000 width=0)
(2 rows)

  • PostgreSQL chooses a sequential scan.

  • Unlike MySQL, PostgreSQL’s planner prefers to read the entire table rather than using an index in this example.

We can see that PostgreSQL chose a completely different execution plan.

Next, let’s disable sequential scans in PostgreSQL and observe how the execution plan changes:

# SET enable_seqscan = off;
SET
# SET max_parallel_workers_per_gather = 0;
SET
# explain select count(*) from orders;
                                              QUERY PLAN
-------------------------------------------------------------------------------------------------------
 Aggregate  (cost=20976.42..20976.43 rows=1 width=8)
   ->  Index Only Scan using idx_orders_customer on orders  (cost=0.42..18476.42 rows=1000000 width=0)
(2 rows)

Now, PostgreSQL uses an Index Only Scan. Notice that the planner estimates a higher cost for this plan compared to the sequential scan, even though it accesses fewer pages.

💰 1.2 Comparing Actual Performance

Let’s now check the actual runtime for these three scenarios, with parallel execution turned off in PostgreSQL.

The results are as follows:

System / Configuration Execution Time
MySQL default ~60 ms
PostgreSQL default ~30 ms
PostgreSQL seq scan disabled ~34 ms

  • Disabling sequential scans forces PostgreSQL to choose a less efficient plan.

  • MySQL’s execution time is roughly twice as long as PostgreSQL’s.

Even though an Index Only Scan accesses fewer pages, PostgreSQL must take the B+ tree characteristics into account during cost estimation. In this scenario, scanning just the index is estimated to be more expensive than performing a sequential scan.

🧠 2. How PostgreSQL Plans Queries

We can now explore how PostgreSQL’s planner really works. Think of it as a careful, analytical strategist: when you submit a SQL query, the planner evaluates multiple possible strategies, estimates their costs, and then selects the plan it believes will execute most efficiently.

🎯 2.1 Define the Objective

The SQL query specifies:

  • Tables involved

  • Filters and predicates

  • Joins and relationships

  • Sorting rules

  • Aggregates

The planner interprets this as a precise target.

🛣️ 2.2 How PostgreSQL Explores the Planning Search Space

The planner evaluates all feasible execution paths.

2.2.1 Access Methods

For a single table, PostgreSQL commonly considers these access paths:

  • Sequential Scan
    PostgreSQL reads the entire table block by block. It does not use any index and simply scans all rows. This is efficient when a large portion of the table must be read.

  • Index Scan
    PostgreSQL uses a B+ tree (or other index type) to locate matching row pointers (TIDs) one by one, then fetches each row from the heap. This is efficient when the filtered rows are few or when the index is highly selective.

  • Index Only Scan

    An Index Only Scan can be used when the index covers all required columns and the visibility map marks the pages as visible, allowing PostgreSQL to return results directly from the index without heap access, resulting in better performance than a regular Index Scan.

  • Bitmap index/heap Scan

    It first performs a Bitmap Index Scan to collect TIDs, then performs a Bitmap Heap Scan to fetch the corresponding rows. This may be beneficial when many rows match the search condition, because it batches TID lookups and reduces random I/O.

Each reflects a different way of reading rows from storage.

2.2.2 Join Algorithms

When joining two tables, PostgreSQL’s planner typically evaluates:

  • Nested Loop
    A join method where PostgreSQL takes one row from the outer table and searches for matching rows in the inner table.

    • Nested loops are the most frequently attempted and commonly used join method.

    • This method generally works very well when the outer table is small or when an index exists on the join key of the inner table.

  • Merge Join
    A join method that requires both inputs to be sorted on the join key and then merges the two sorted streams by advancing pointers through each list.

    • Merge joins are generally efficient for large, already-sorted datasets.

  • Hash Join
    A join method where PostgreSQL builds a hash table from the smaller input using the join key and then probes it with rows from the larger input to find matches.

    • Hash joins are extremely common when executing bushy joins.

    • This method generally performs very well when both inputs are unsorted and the join key has a good hash distribution.

These are the fundamental building blocks for combining data across multiple tables.

It is worth noting that MySQL primarily relies on Nested Loop joins, with Hash Joins supported only in limited scenarios, making its join strategy generally less flexible than PostgreSQL’s.

2.2.3 Join Orders

To choose the optimal join order, PostgreSQL explores:

  • Most valid pairings and permutations of the tables
    The planner enumerates legal join combinations to cover as many feasible join orders as possible.

  • Dynamic programming to avoid redundant calculations
    The planner reuses previously computed results for subsets of tables, so it does not recalculate join costs repeatedly.

  • Partitioning the join search space for large queries
    By default, when a query involves more than eight tables, PostgreSQL splits the join graph into smaller partitions to keep the dynamic programming search from becoming too costly.

  • GEQO (Genetic Query Optimization) for very large join graphs
    For extremely large queries, PostgreSQL could use a genetic algorithm to sample and evolve join orders instead of exhaustively enumerating them.

Together, the combination of access methods, join algorithms, and join orders creates a vast space of possible plans, with each combination representing a different path through the data.

This level of flexibility far exceeds what MySQL can achieve, making it one of the key strengths of PostgreSQL’s planner.

🚦 2.3 Evaluate Costs

The planner may estimate the cost for each path using:

  • Histograms from pg_statistic

  • Most Common Values (MCV)

  • Distinct value counts (NDV)

  • Column correlation factors

  • Table size and page counts

  • Memory limits (work_mem)

  • CPU and I/O costs

Every path may get:

  • Estimated row counts

  • Startup and total costs

🧩 2.4 Upper Paths

These upper paths handle higher-level operations, including:

  • Aggregates

  • Sorting

  • DISTINCT

  • LIMIT

  • Window functions

  • Parallel execution

They build on the base paths generated in earlier steps, adding additional layers of processing before the planner selects the final execution plan.

✂️ 2.5 Prune Unpromising Paths

The planner retains only the paths it considers potentially optimal for each subset of tables, discarding inferior join orders or alternatives with significantly higher costs before constructing larger joins. In theory, the chosen plan may not always be perfectly optimal, but in most real-world scenarios, it performs very well in practice.

🏁 2.6 Select the Path the Planner Considers Best

Under normal circumstances, the planner picks the lowest-cost path, which then forms the final Plan Tree that guides query execution.

🧩4. PostgreSQL Extensions: Expanding Planner Capabilities

PostgreSQL’s planner is already powerful, but one of its greatest strengths is extensibility. Extensions are modules that can introduce new data types, functions, operators, indexes, or even enhance the planner itself.

These extensions can influence how queries are planned and executed, providing developers with flexible tools to optimize or extend the database’s behavior.

🔹 4.1 How Extensions Interact with the Planner

Extensions can enhance or modify PostgreSQL’s planner in several ways:

  1. New Access Methods

    • Custom index types (e.g., GiST, SP-GiST, GIN, BRIN) provide alternative scan paths.

    • The planner evaluates these indexes alongside built-in access methods to determine the most efficient path.

  2. Planner Hooks

    • Extensions can register hooks to influence planning decisions.

      For example, a hook might modify path cost estimates or add custom paths for specialized queries.

  3. Custom Functions and Operators

    • Functions with selectivity estimates help the planner better assess filter effectiveness.

    • Operator classes define how new data types interact with indexes, enabling more efficient query execution.

🔹 4.2 Practical Benefits

  • Faster execution for specialized queries
    Advanced index types or spatial operations can significantly speed up targeted queries.

  • Safe testing of hypothetical indexes
    Extensions allow evaluating potential indexes without modifying the physical schema, helping with optimization planning.

  • Domain-specific planner enhancements
    Custom logic can be added to optimize queries for particular applications or data patterns beyond the built-in planner capabilities.

🗑️ 6. How Dead Tuples Affect Query Planning

1. Statistics Depend on Live Tuples

  • PostgreSQL’s planner uses statistics from pg_statistic to estimate row counts, distinct values, and data distribution.

  • Dead tuples are ignored in these statistics if ANALYZE has been run recently, so the planner mostly sees only live data.

2. Table Bloat Can Affect Cost Estimates

  • Although dead tuples don’t affect statistics, sequential scans still read all table pages, including dead tuples, unless the table has been vacuumed.

  • This may cause the planner to underestimate I/O costs, sometimes resulting in suboptimal plans.

3. Index Only Scans Depend on Visibility Maps

  • Dead tuples can prevent Index Only Scans from being fully efficient because pages with dead tuples might not be marked as “all-visible,” requiring heap access.

🎯 Key Takeaways

  • PostgreSQL’s planner is the core intelligence behind query execution.

  • It explores many possible paths and estimates their costs, pruning suboptimal options along the way.

  • Accurate statistics, proper indexing, and understanding planner behavior are crucial for performance.

  • Mastering the planner transforms query optimization from guesswork into a systematic engineering process.
