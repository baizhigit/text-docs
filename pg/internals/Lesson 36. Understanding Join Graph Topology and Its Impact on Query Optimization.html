🗺️ Understanding Join Graph Topology and Its Impact on Query Optimization

Why do some multi-table join queries run quickly while others perform poorly?

The answer may lie in the join graph topology, which illustrates how tables are connected through join conditions. Like a city map guiding traffic flow, the structure of your joins may determine how efficiently PostgreSQL plans a query.

In this lesson, you will learn how join topology influences planner decisions, why certain join orders are cheaper, and how to use this understanding to write faster queries and analyze execution plans more effectively.

📊 Types of Join Graph Topology

First, let's take a look at the different types of Join Graph Topology.

🔗 Chain Join

Tables are joined one after another in a linear sequence, with each table connected to at most two neighbors. For example, A JOIN B JOIN C JOIN D forms a straight line.

Planner Behavior:

  • The search space is small and well-structured. Dynamic Programming (DP) handles chain joins very efficiently.

  • Cost differences between good join orders are usually minor.

Typical Use Cases:

  • Normalized OLTP schemas with linear foreign key relationships, e.g., customers → orders → order_items → shipments.

Practical Tips:

  • The default dynamic programming (DP) planner usually performs well, so using GEQO is generally not necessary.

  • If some tables are much bigger than others, you can try changing the join order, but usually the DP planner finds a good plan by itself.

⭐ Star Join

A star has a central fact table joined to many dimension tables.

Planner behavior:

  • Small dimension tables: The planner may use index lookups, so full table scans are avoided.

  • Large dimension tables: It may choose hash joins to combine them efficiently with the fact table.

  • Dynamic Programming (DP) works well for Star Joins with a moderate number of tables.

  • DP usually produces left-deep or right-deep trees. Trying bushy join orders in this case is usually less effective.

When it appears:

  • Data-warehouse star schema queries: fact table with many dimension joins (time, product, store, customer…).

Practical tip:

  • Make sure dimension tables have highly selective filters and indexes. When several dimensions are selective at the same time, the planner may use hash or merge joins for better performance.

Example:

From the trace log, the planner explored about 45,000 candidate paths, roughly 32,000 of which were bushy-join candidates. However, the final plan was a right-deep join tree. In other words, the planner spent a lot of time evaluating bushy joins, but they provided little benefit for this query.

🧩 Dense Join

A dense join involves many tables connected to each other, forming a complex and highly interconnected join structure.

Planner behavior:

  • Finding the optimal plan often requires pairing subtrees (for example, (A⋈B) combined with (C⋈D)) instead of following a strict left-deep or right-deep tree order. This makes MySQL less suitable for very complex joins.

  • DP becomes infeasible as n grows too large, so at this point we need the planner to switch to GEQO.

When it appears:

  • Complex analyses that involve many normalized tables or ad-hoc joins with lots of foreign-key relationships, forming a graph-like structure.

Practical tip:

  • For dense joins, increase the planner’s time budget or let GEQO run with a properly tuned geqo_effort.

  • Indexes alone are usually not enough. Focus on semantic optimizations such as pushing down filters, pre-aggregating data, rewriting joins, or reducing cardinality.

📌 Summary

  • Topology Matters: Chain, star, and dense joins affect the planner’s search space and overall performance.

  • Chain Joins: These are simple, linear joins. DP handles them efficiently, so GEQO is usually unnecessary.

  • Star Joins: A fact table joined with many dimension tables. Left or right deep trees are common, and hash joins work well.

  • Dense Joins: Many highly interconnected tables. DP struggles as the number of tables grows, making GA increasingly suitable.
