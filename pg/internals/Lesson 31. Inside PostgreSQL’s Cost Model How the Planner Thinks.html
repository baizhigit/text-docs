⚖️ Inside PostgreSQL’s Cost Model: How the Planner Thinks

Explore how PostgreSQL calculates the cost of each path and selects execution plans. Understand how these cost estimates influence query performance.

🧐 1. Why Understanding Cost Matters

PostgreSQL does not blindly execute queries. Most SQL statements go through a planning phase, where the planner estimates costs for different execution paths and chooses the one expected to be the most efficient.

Think of it like planning a trip. You don’t just take the first route you see. You consider traffic, distance, and road conditions. PostgreSQL does the same with your data.

Understanding the cost model helps you:

  • Predict why certain indexes or join methods are chosen

  • Optimize queries by adjusting statistics, indexes, or planner parameters

  • Avoid surprises with complex joins or large tables

⚖️ 2. What the Cost Model Actually Represents

In PostgreSQL, cost is an abstract unit of work, not actual time or money.

Each plan node has:

  1. Startup Cost – cost to produce the first row

    • Important for queries with LIMIT, where lower startup costs may be preferred.

  2. Total Cost – estimated cost to process all rows

    • total_cost = startup_cost + run_cost

Example:

Plan Startup Cost Total Cost
Seq Scan on large_table 0.0 5000.0
Index Scan using idx_col 0.5 2000.0

Even with a slightly higher startup cost, the index scan wins for large result sets.

Analogy:

  • Startup cost = time to start the engine

  • Total cost = total fuel needed to reach your destination

🔍 3. Components of PostgreSQL’s Cost Model

Here we only look at the main components of the single-node PostgreSQL cost model and ignore network costs in distributed settings.

💻 3.1 CPU Costs

  • Processing each row

  • Evaluating WHERE, JOIN, ORDER BY

  • Function calls

  • Other internal CPU work

📀 3.2 I/O Costs

  • Number of disk pages expected to be read

  • Cost parameters:

    • seq_page_cost (default 1.0)

    • random_page_cost (default 4.0)

The planner treats these as abstract units; actual I/O may vary depending on whether pages are already in the shared buffer cache.

🌐 3.3 Parallel Costs

  • Startup costs for worker processes

  • CPU cost divided among workers

  • Planner accounts for parallel coordination overhead

🧭 4. How the Planner Explores Execution Paths

PostgreSQL does not try every possible execution path:

  • For small queries, it uses Dynamic Programming (DP) with pruning.

  • For large queries, if the number of joins to analyze is greater than or equal to geqo_threshold and join collapse does not occur, PostgreSQL use the Genetic Algorithm (GA) to find a join order.

Key Concepts:

  • Paths: possible access methods for tables or joins

  • Parent-Child Relations: links paths in planner structure

  • Pruning: discard clearly expensive paths early

Example: Query joining A JOIN B JOIN C

  1. Consider different join orders: (A JOIN B) JOIN C, (B JOIN C) JOIN A

  2. Evaluate join methods: nested loop, hash join, merge join

  3. Evaluate table access: seq scan, index scan, bitmap scan

  4. Consider parallel execution

  5. Discard paths with higher cost

Think of it like planning a road trip. You consider different routes, but immediately ignore options that are clearly inefficient. The planner works the same way for join orders.

🧮 5. How PostgreSQL Calculates Costs

PostgreSQL’s planner examines table statistics and estimates a “cost” for each possible path. It then chooses the path that it expects will complete the query with the least effort.

📊 5.1 Table Statistics

PostgreSQL relies on table-level metadata:

  • pg_class.reltuples — estimated number of rows

  • pg_class.relpages — estimated number of pages

  • ANALYZE updates these statistics to reflect current data distribution

These statistics help the planner understand the size and density of a table, which in turn guides its decisions on how to scan or join it efficiently.

🎯 5.2 Selectivity Estimates

Selectivity determines how many rows will survive filtering or join conditions:

  • Fraction of rows surviving a WHERE clause

  • Fraction of rows matching a join predicate

PostgreSQL uses histograms and most-common-values (MCV) lists to make these predictions more accurate.

🔗 5.3 Join Costs

PostgreSQL uses different cost models for each join strategy. The formulas below give a simple, high-level view of how the planner estimates costs, without considering parallel execution.

Note that the actual cost calculations inside PostgreSQL are more complex. What we show here is only a simplified version.

5.3.1 Nested Loop Join (NLJ)

Total_cost = Startup_cost + Run_cost
Run_cost   = Cost_outer_scan + (N_outer × Cost_inner_lookup)

The value of Cost_inner_lookup depends on how the inner table is accessed:

Seq Scan:
  Cost_inner_lookup ≈ full scan cost of the inner table

Index Scan:
  Cost_inner_lookup ≈ index traversal + fetching matching heap rows

Index-Only Scan:
  Cost_inner_lookup ≈ index traversal only

Behavior:

  • Highly efficient for small outer tables

  • Can become very expensive without indexes, because each outer row triggers a potentially costly inner lookup

5.3.2 Hash Join

Total_cost = Startup_cost + Run_cost
Run_cost   = Build_cost + Probe_cost

  • Build_cost: scan the inner table and construct an in-memory hash table

  • Probe_cost: scan the outer table and probe the hash table for matches

⚠️ When the hash join spills to disk because there isn’t enough memory, its cost increases sharply.

Behavior:

  • Ideal when the build side can fit in memory

  • Designed for equality joins

5.3.3 Merge Join

Total_cost = Startup_cost + Run_cost
Run_cost   = left_sort_cost + right_sort_cost + merge_cost

  • Sort cost: required if inputs are not already sorted on join keys

  • Merge cost: sequentially walk through sorted inputs to match join keys

Using index scans on ordered columns can eliminate the need to sort entirely.

Behavior:

  • Generally efficient for large, sorted inputs

  • Good for equality and range joins

  • Sorting can dominate cost when no useful order exists

Note:

PostgreSQL estimates merge join costs conservatively.

As a result, merge joins that could be very fast in practice are sometimes not chosen, because their estimated cost looks too high.

PostgreSQL assigns the same estimated cost to these two queries, even though their actual execution times differ by hundreds of times. The main reason is that, when estimating merge join costs, the planner does not analyze the WHERE conditions in detail and instead uses a simple, rough estimation method. This causes the cost to remain high even in cases where the query actually runs very fast.

💡5.4 Join Method Comparison

Join Type Strengths Weaknesses
Nested Loop Small outer tables Slow for large tables without indexes
Hash Join Ideal when the build side can fit in memory Needs memory for hash table
Merge Join Generally efficient if inputs pre-ordered Sorting can be expensive; often suppressed

PostgreSQL picks the plan with the lowest estimated total cost, but the actual execution may differ due to caching, data distribution, or outdated statistics.

Interestingly, MySQL often estimates hash join costs using formulas meant for nested loops. This overestimates hash join costs and can prevent them from being chosen by the planner.

⚠️ 6. Why Planner Estimates Can Be Wrong

Even the best cost model can be wrong. PostgreSQL’s planner relies on statistics and assumptions, which sometimes leads to underestimates or overestimates of query costs. Common causes include:

  • Outdated or incomplete statistics — If tables change frequently but ANALYZE is not run, the planner may misjudge row counts and data distribution.

  • Correlated columns — The planner usually assumes column values are independent. When they aren’t, join selectivity and filter effectiveness can be misestimated.

  • Skewed or non-uniform data — Highly skewed distributions or “hot” values can mislead the planner.

Tip: Regularly run ANALYZE and consider custom statistics (CREATE STATISTICS) for columns with unusual distributions or strong correlations. This gives the planner better information for more accurate cost estimates.

📈 7. Single-Table Example

Let’s analyze a simple query where id is the primary key and orders_pkey is a B+ tree index on the id column:

EXPLAIN SELECT * FROM orders WHERE id = 1;

The planner evaluates multiple access paths and estimates their costs:

Method Startup Total
Seq Scan 0.00 17,906
Index Scan 0.42 8.44
Bitmap Heap Scan 4.43 8.45
Gather (parallel) 1000.00 11,614.43

PostgreSQL chooses the Index Scan because it has the lowest estimated total cost.

From this sequence diagram, we can observe several key behaviors:

  • Single-table access: PostgreSQL keeps only the cheapest path in this example. Any less efficient path is immediately discarded.

  • Parallel paths: Gather (parallel) paths are considered only if a sequential scan might benefit from parallel execution. Even simple lookups are evaluated for potential parallelism.

  • Comprehensive evaluation: PostgreSQL systematically compares all access strategies, estimates their costs, and applies cost-based pruning.

  • Cost-based decisions: Unlike MySQL, PostgreSQL consistently relies on cost estimates rather than heuristics, following a cost-based approach even when the optimal choice seems obvious.

🧩 8. Two-Table Join Example

Here we analyze a join between two tables. 

EXPLAIN SELECT orders.id, customers.name 
FROM orders 
INNER JOIN customers ON orders.customer_id = customers.id;

Below is a simplified sequence diagram illustrating the planner’s decision process during add_path.

Join planning for two tables produces far more candidate paths than single-table planning.

When PostgreSQL plans a join between two tables, it evaluates multiple alternatives, including the following:

  1. Single-table access methods
    The planner evaluates all possible ways to scan each table, including whether parallel execution can be used.

  2. Join order
    With two tables, only two orders exist (A ⋈ B or B ⋈ A). Even so, in this example the planner still explores over thirty candidate paths.

  3. Nested loop paths
    Nested loops make up the majority of candidate paths and are the most commonly evaluated join method, especially when indexes are available.

  4. Parallel execution candidates
    The planner generates parallel join options using partial paths. These partial-path lists coexist with normal path lists as two separate sets during planning.

  5. Multiple surviving paths
    At each planning stage, PostgreSQL may retain more than one candidate path for the same relation or join, depending on different pathkeys (ordering requirements).

  6. Early pruning
    Based on trace logs, PostgreSQL eliminates unlikely or overly expensive candidates early using mechanisms such as add_path_precheck, which significantly reduces planning overhead.

  7. Join methods
    The planner evaluates nested loop, hash join, and merge join methods, considering all valid combinations of tables A and B for each method.

Gaining an intuitive understanding of how the planner evaluates paths from this sequence diagram will make it easier to follow its behavior later. Understanding how PostgreSQL handles simple joins is an important step in learning the planner.

🔧 9. Can Extensions Influence Planner Costs in PostgreSQL?

PostgreSQL extensions cannot directly modify the planner’s internal cost formulas, but they can indirectly influence planner behavior in several ways:

  1. Custom Scan Methods
    Define a CustomScan node with its own cost function, allowing the planner to consider your custom operation using your specified cost model.

  2. Planner Hooks
    Hooks like planner_hook and set_rel_pathlist_hook let extensions add new paths or modify existing ones. You can adjust the costs of these paths to steer the planner toward preferred execution strategies.

  3. Statistics and Selectivity
    By providing extended statistics or influencing selectivity estimates, an extension can indirectly affect how the planner evaluates scan and join costs.

Key takeaway: Extensions cannot rewrite PostgreSQL’s internal cost formulas, but they can shape planner decisions by adding custom paths, adjusting path costs, or influencing selectivity.

This provides developers a powerful way to experiment with query optimization without changing PostgreSQL’s planner source code.

🎯 10. Takeaways

  • Cost-Based Decisions
    PostgreSQL estimates startup and total costs for all candidate paths and selects the plan with the lowest estimated total cost. This applies to scans, joins, and parallel execution.

  • Single-Table vs. Join Planning

    • Single-table queries: only a few paths are considered.

    • Joins: the number of candidate paths grows rapidly; even two tables can generate 30+ paths.

  • Join Strategies
    The planner evaluates nested loop, hash join, and merge join, considering all valid table access methods and path orderings.

  • Parallel Execution
    Partial paths allow parallel options, which coexist with normal paths.

  • Early Pruning
    PostgreSQL discards clearly expensive paths early using mechanisms such as add_path_precheck, which significantly reduces planning overhead.

  • Statistics and Selectivity
    Accurate table statistics and selectivity estimates are critical. Outdated stats, correlations, or skewed data can mislead the planner.

  • Extensions
    While extensions cannot modify internal cost formulas, they can influence planning via custom scans, hooks, and extended statistics, enabling safe experimentation without changing the core planner.
