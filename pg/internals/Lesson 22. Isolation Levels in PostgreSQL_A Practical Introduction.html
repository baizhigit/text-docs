⚖️ Isolation Levels in PostgreSQL: A Practical Introduction

Isolation isn’t just about correctness; it’s about finding the right balance between consistency and concurrency. Understanding how PostgreSQL enforces isolation helps you write safe, reliable, and performant queries.

📌 1. What Are Isolation Levels?

In a multi-user database, isolation levels define how and when the effects of one transaction become visible to others.

The four standard SQL isolation levels:

Level Description
Read Uncommitted May see uncommitted data from other transactions (dirty reads)
Read Committed Each statement sees only committed data at its start
Repeatable Read A transaction sees a consistent snapshot taken at BEGIN
Serializable The strictest level ensures that transactions behave as if they were executed sequentially.

PostgreSQL implements all four, but note that:

READ UNCOMMITTED behaves identically to READ COMMITTED because PostgreSQL never exposes dirty reads. In practice, PostgreSQL effectively provides three distinct levels: READ COMMITTED, REPEATABLE READ, and SERIALIZABLE.

Default level: READ COMMITTED
Common alternative: REPEATABLE READ for stable snapshots
SERIALIZABLE is preferred for critical data correctness.

🔄 2. Read Committed — Seeing the Latest Committed Data

Behavior:
Every query inside a transaction sees the most recently committed data at the moment that query starts.

Example:

-- T1
BEGIN;
SELECT stock FROM products WHERE id = 100;

-- T2
UPDATE products SET stock = stock - 10 WHERE id = 100;
COMMIT;

-- Back to T1
SELECT stock FROM products WHERE id = 100;

➡️ The second query in T1 will see the updated stock from T2.

Pros: Always sees up-to-date data
Cons: Results within a single transaction may change between queries

Internals:

  • Each query takes a fresh snapshot of active transactions.

  • MVCC checks tuple visibility using xmin, xmax, and the CLOG.

  • Reads never block writes, and vice versa, which is ideal for high concurrency.

⚠️ Under heavy concurrency (200+ concurrent transactions), maintaining snapshots can become costly in NUMA environments. This is essentially a well-known high-concurrency issue for the READ COMMITTED isolation level.

Think of it as:

“Every query sees the world as it is right now.”

🧰 3. Repeatable Read — Stable Snapshot for the Whole Transaction

Behavior: The transaction sees the same snapshot throughout, regardless of other commits.

Example:

-- T1
BEGIN;
SELECT stock FROM products WHERE id = 100;

-- T2
UPDATE products SET stock = stock - 10 WHERE id = 100;
COMMIT;

-- Back to T1
SELECT stock FROM products WHERE id = 100;  -- Sees the old value

➡️ T1 still sees the original data, as it is working on its own snapshot.

Pros: Fully consistent reads within the same transaction
Cons: Doesn’t reflect concurrent updates

How PostgreSQL does it:

  • Takes a transaction snapshot at the first query after the transaction begins.

  • The snapshot lists visible transaction IDs.

  • Each read checks tuples against this snapshot using xmin / xmax.

Best for:

  • Reporting or analytics

  • Financial transactions

  • Long-running reads that require stable results

Analogy:
“You take a photograph of the database at the first query after the transaction begins; every subsequent query in the transaction uses that same photograph.”

🧩 PostgreSQL vs MySQL in Repeatable Read

It should be noted that PostgreSQL’s repeatable read (RR) isolation level does not have the same SELECT … FOR UPDATE locking capability as MySQL.

For example:

Step Session A Session B
1 BEGIN ISOLATION LEVEL REPEATABLE READ; BEGIN ISOLATION LEVEL REPEATABLE READ;
2 select * from users where id < 10 for update;
3 insert into users values(4, '4');
4 select * from users where id < 10 for update;

As shown in the diagram above, in PostgreSQL, the INSERT in Session B still executes immediately without waiting. In MySQL, under the same conditions, Session A would block Session B. This highlights an important difference under REPEATABLE READ, which users coming from MySQL should be aware of.

When PostgreSQL acts as a foreign data wrapper (FDW) client to another PostgreSQL server, the backend access level defaults to REPEATABLE READ.

🔐 4. Serializable — Strictest Isolation

Behavior:
Transactions behave as if executed one by one, preventing all anomalies (dirty reads, non-repeatable reads, and phantoms).

Implementation Details:

  • PostgreSQL uses Serializable Snapshot Isolation (SSI).

  • It tracks read–write dependencies between concurrent transactions.

  • When a conflict pattern is detected, PostgreSQL aborts one transaction to preserve correctness.

Pros: True serializability with acceptable performance
Cons: Slightly higher CPU usage and possible transaction retries

Analogy:

Serializable = “Optimistic concurrency with built-in anomaly detection.”

⚖️ Comparing SERIALIZABLE Isolation: PostgreSQL and MySQL

  • PostgreSQL’s SERIALIZABLE implements true serializability using Serializable Snapshot Isolation (SSI). It detects and resolves conflicts without heavy locking, allowing concurrent transactions to run safely. This approach ensures strict consistency with moderate performance overhead in many workloads.

  • MySQL’s SERIALIZABLE is implemented as a lock-based serializable level. It relies on standard row-level locks to enforce serializability, which can reduce concurrency and increase contention under high update workloads.

Both provide strict isolation, but the internal mechanisms differ: PostgreSQL uses conflict detection, while MySQL relies on blocking.

✅ Common Transaction Anomalies and What Each Level Prevents

Anomaly / Conflict READ COMMITTED REPEATABLE READ SERIALIZABLE
Dirty Read ❌ Prevented ❌ Prevented ❌ Prevented
Non-Repeatable Read ✔️ Possible ❌ Prevented ❌ Prevented
Phantom Read ✔️ Possible ❌ Prevented ❌ Prevented
Write Skew ✔️ Possible ✔️ Possible ❌ Prevented
Full Serialization Conflicts ❌ Not detected ❌ Only partially detected ❌ Prevented (all detected)

💡 Explanation

  • READ COMMITTED: Only prevents dirty reads. Each statement sees a fresh snapshot, so non-repeatable and phantom reads can happen.

  • REPEATABLE READ: Uses a fixed snapshot for the whole transaction, preventing non-repeatable and phantom reads. However, write skew anomalies are still possible. PostgreSQL may abort a transaction only when there is a direct row-level conflict to maintain consistency, such as the common could not serialize access due to concurrent update error.

  • SERIALIZABLE: Adds conflict detection (SSI) on top of snapshots. It guarantees full serializability by aborting any transaction that could cause inconsistent results.

🧩 Example: Preventing Write Skew under SERIALIZABLE

Let’s see how PostgreSQL’s Serializable Snapshot Isolation (SSI) prevents a write skew anomaly, a situation where two concurrent updates could both violate a rule such as “At least one doctor must always be on duty.”

Session 1:

BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
SELECT COUNT(*) FROM on_call WHERE on_duty = TRUE;  -- returns 2
UPDATE on_call SET on_duty = FALSE WHERE doctor = 'Alice';
COMMIT;

Session 2 (runs concurrently):

BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
SELECT COUNT(*) FROM on_call WHERE on_duty = TRUE;  -- also returns 2
UPDATE on_call SET on_duty = FALSE WHERE doctor = 'Bob';
COMMIT;
-- ERROR: could not serialize access due to read/write dependencies...

⚙️ 5. Practical Guidelines

  • Read Committed: Fast, up-to-date — best for OLTP and web apps

  • Repeatable Read: Stable snapshots — ideal for analytics or finance

  • Serializable: Strict correctness — best for mission-critical data consistency

Always choose the isolation level based on workload patterns and consistency needs.

🎯 6. Key Takeaways

  • Isolation levels define how transactions see each other’s changes.

  • PostgreSQL enforces them using MVCC, snapshots, and CLOG.

  • READ COMMITTED → fresh but possibly changing data

  • REPEATABLE READ → consistent snapshot per transaction

  • SERIALIZABLE → strictest, anomaly-free behavior

Understanding isolation levels is fundamental for writing correct, predictable, and high-performance PostgreSQL applications.
