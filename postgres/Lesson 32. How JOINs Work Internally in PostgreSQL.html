🔗 How JOINs Work Internally in PostgreSQL

JOINs connect related rows across tables and are the core of relational database power. In PostgreSQL, JOIN execution involves a sophisticated planner and multiple join algorithms. Understanding how PostgreSQL builds and executes JOINs helps you write faster, more efficient SQL.

If you’ve ever wondered:

  • “Why does my JOIN run slowly?”

  • “How does PostgreSQL decide between nested loop, hash join, or merge join, and why does MySQL mainly rely on nested loop?”

The planner lessons will guide you through all of these questions, covering everything from basic concepts to PostgreSQL’s internal execution flow.

📘 1. What Exactly Is a JOIN?

A JOIN combines rows from two or more tables based on matching columns.

Example tables:

  • users — stores user info (id, name)

  • orders — stores purchases linked by user_id

SELECT u.name, o.item
FROM users u
JOIN orders o ON u.id = o.user_id;

JOIN answers the fundamental relational question of who bought what.

🔍 2. Types of JOINs in PostgreSQL

PostgreSQL supports standard SQL join types:

2.1 INNER JOIN

Returns only rows that match in both tables.

SELECT * 
FROM users u
INNER JOIN orders o ON u.id = o.user_id;

✅ Use INNER JOIN when you want results that exist in both tables.
Tip: INNER can be omitted; it’s the default.

In PostgreSQL, A INNER JOIN B produces the same result as B INNER JOIN A. When generating join paths for an inner join between two tables, the planner does not split the candidate paths into separate lists.

2.2 LEFT JOIN

Returns all rows from the left table, filling NULL when there’s no match on the right.

SELECT * 
FROM users u
LEFT JOIN orders o ON u.id = o.user_id;

✅ Use LEFT JOIN to include all users, even those without orders.

A LEFT JOIN is not the same as reversing the tables (B LEFT JOIN A). The planner must treat them differently. LEFT JOINs often limit optimization opportunities. When business logic allows, converting a LEFT JOIN to an INNER JOIN is a common performance improvement. In one real case, simply changing complex LEFT JOINs to INNER JOINs without affecting correctness improved query performance by up to 10 times.

2.3 RIGHT JOIN

The mirror of LEFT JOIN. Rarely used in practice, usually tables are swapped and a LEFT JOIN is used instead.

SELECT *
FROM orders
RIGHT JOIN users ON users.id = orders.user_id;

Similarly, A RIGHT JOIN B ≠ B RIGHT JOIN A.

2.4 FULL OUTER JOIN

Returns all rows from both tables, filling NULL where there’s no match.

SELECT * 
FROM users u
FULL JOIN orders o ON u.id = o.user_id;

For FULL JOIN, A FULL JOIN B is the same as B FULL JOIN A.

2.5 CROSS JOIN

Cartesian product: every row from users with every row from orders.

SELECT * FROM users CROSS JOIN orders;

⚠️ Use with caution! Result size grows rapidly (e.g., 10 users × 10 orders = 100 rows).

Like INNER JOIN, A CROSS JOIN B = B CROSS JOIN A.

2.6 SEMI / ANTI JOIN (Internal)

Not directly written in SQL. PostgreSQL uses these for EXISTS or NOT EXISTS.

  • SEMI JOIN: returns rows from the left table if a match exists on the right.

  • ANTI JOIN: returns rows from the left table if no match exists on the right.

Both return only columns from the left table. These internal join types are handled specially, which significantly increases the planner's complexity.

🔑3. Join Algorithms in PostgreSQL

PostgreSQL’s planner can choose among:

  1. Nested Loop Join — generally ideal when one side is small and/or indexed.

  2. Hash Join — builds a hash table in memory; highly efficient, and essential for maintaining good performance in complex multi-table joins.

  3. Merge Join — requires sorted inputs; generally efficient when joining already ordered data.

N-way joins are represented as a series of 2-way joins. The planner generally prefers joins with explicit conditions, especially in multi-table queries, and delays Cartesian joins as much as possible. To determine the optimal join order, the planner typically uses dynamic programming. For very large join queries, PostgreSQL also provides genetic algorithms that users can leverage.

3.1 How Nested Loop Join Works

We will explain how a Nested Loop Join works using a concrete example.

Consider the following SQL query:

SELECT orders.id, customers.name 
FROM orders 
INNER JOIN customers 
  ON orders.customer_id = customers.id
where customers.id < 3;

  1. PostgreSQL’s current Merge Join is not very efficient when one table is large but only a few rows actually match. One possible improvement would be to jump directly to the next matching key using a binary-search approach instead of scanning each row one by one.

  2. If neither input is already sorted, PostgreSQL must perform sorting steps, which can be expensive. Merge Join works best when both inputs arrive pre-sorted.

  3. Trace logs show that PostgreSQL first looks up each row’s TID using the index, then fetches the full row from the heap for both the orders and customers tables. When the join has to compare many rows, this two-step access becomes expensive and could slow down execution significantly.

Key Points

  1. Build Phase

    • Scan the inner table (customers).

    • Compute a hash on each row’s join key and insert the row into a hash table.

    • The hash table allows fast lookups later.

  2. Probe Phase

    • Scan the outer table (orders).

    • Compute the hash of each outer row’s join key.

    • Look up matching rows in the hash table and output joined results.

  3. Characteristics of Hash Join

    • Efficient for joining a small table (inner) with a large table (outer).

    • Inner table is scanned once; outer table probes the hash table.

    • Performance relies on the inner table fitting in memory.

    • Probing the hash table for matching records is much faster than accessing a B+ tree under the same conditions.

Hash Join is highly effective when conditions allow, especially for large, unsorted datasets.

These three join methods are key to handling complex joins efficiently. MySQL does not support Merge Join and offers only limited Hash Join capabilities, which is one reason its join performance is often much lower than PostgreSQL.

📘 4. Join Planning and Optimization Strategies

Here, we’ll show how join conditions and the number of tables affect how the planner decides the join order.

Join conditions guide the planner and reduce result size

  • Join conditions help the planner determine which tables are related and remove unnecessary join orders. Without them, the planner must consider many more possibilities, slowing down planning.

  • They also reduce the result set, avoiding a Cartesian product and minimizing the database’s workload.

Effect of table count on planning

  • More tables increase complexity and slow down the planner.

  • For a small number of tables, PostgreSQL uses dynamic programming (DP) to find the optimal join order.

  • For larger joins, DP can become too slow. PostgreSQL can split the join graph and apply DP within each partition, though this is not always very effective.

  • For very large numbers of tables, PostgreSQL can use a genetic algorithm to reduce planning cost.

Overall, PostgreSQL provides a powerful and flexible join planning mechanism, enabling it to handle complex joins much better than MySQL.

Trace analysis shows that the search space for join paths is much larger than the number of possible join orders. Pruning unnecessary paths is crucial and a major reason PostgreSQL achieves efficient join planning.

🌳 5. Join Tree Structures

A database cannot join all tables at once, so it processes joins two tables at a time. This leads to the concept of join tree structures, which define how multiple table joins are organized and executed.

Below are the three basic types of join tree structures.

5.1 Left-deep Tree

Left-deep tree characteristics:

  • Joins form a linear chain, with the right side of each join always being a base table.

  • Supports efficient pipelined execution.

  • Indexes can be used efficiently because the inner table in each join is always a base table that can have indexes.

5.2 Right-deep Tree

Right-deep tree characteristics:

  • Joins are performed sequentially from right to left, forming a linear chain.

  • The left input (outer table) of each join is always a base table.

  • Useful for pipelined execution in some cases.

5.3 Bushy Tree

Bushy tree characteristics:

  • Joins are performed in a more flexible, non-linear order.

  • Both left and right sides can be complex subtrees.

  • Explores more join combinations, which can lead to lower-cost plans, but significantly increases the search space.

5.4 Comparison: MySQL vs PostgreSQL Join Trees

Feature MySQL PostgreSQL
Default join tree type Left-deep tree Left-deep, Right-deep, Bushy tree
Flexibility Limited; only left-deep sequences explored High; can explore multiple tree shapes for better plans
Search space Smaller Much larger

Note that in PostgreSQL, the actual join tree is often a combination of the basic types, not exactly like the examples above.

🧩 6. When JOINs Become Slow

JOIN performance can degrade due to several factors:

  • Poor statistics – the planner may choose suboptimal join methods.

  • Missing indexes – forces full table scans, increasing I/O.

  • Joining too many rows – Cartesian products can dramatically increase result size.

  • Complex joins across multiple large tables – raises both planning and execution cost.

  • Randomized index or heap access – significantly increases I/O.

  • Rigid planner parameters – cost estimates may deviate from actual execution.

  • Inherent PostgreSQL issues – Some cost estimates may not accurately reflect data distribution or actual execution, which can result in suboptimal plans.

Tips for Optimization

  • Use trace tools
    Understand how PostgreSQL plans joins to build a solid foundation for troubleshooting and performance tuning.

  • Keep queries simple
    Avoid putting everything into a single complex query. Large, deeply nested joins are difficult to debug and optimize.
    When possible, consider splitting queries at the application layer.

  • Optimize JOIN usage
    Replace LEFT JOINs with INNER JOINs when business logic allows.
    Create appropriate indexes on join and filter columns to reduce scan costs and improve performance.

  • Tune planner-related parameters
    Adjust settings such as work_mem, enable_hashjoin, enable_mergejoin, and join_collapse_limit to help the planner generate more efficient join plans.

  • Leverage parallel execution
    Enable parallel query execution when appropriate (max_parallel_workers_per_gather). Large table scans and joins can benefit significantly from parallelism on multi-core systems.

  • Other considerations
    Keep table statistics up to date so the planner can choose better join methods. Always specify proper join conditions to avoid unintended Cartesian products.

There are many more ways to optimize than what we listed here, and each problem needs its own analysis.

🧠 7. Summary

  • PostgreSQL executes JOINs using Nested Loop, Hash Join, and Merge Join, organized as join trees.

  • Join conditions and table count strongly affect join order selection and planning complexity.

  • PostgreSQL explores a large space of join paths and relies on pruning to find efficient plans.

  • JOIN performance depends on statistics, indexes, query complexity, cost estimates, and parallelism.

  • Proper query design, indexing, and planner tuning are key to good JOIN performance.

In general, PostgreSQL’s flexible planner enables significantly more efficient JOIN processing than MySQL.
