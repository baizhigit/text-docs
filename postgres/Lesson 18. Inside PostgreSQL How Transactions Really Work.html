⚡ Inside PostgreSQL: How Transactions Really Work

PostgreSQL isn’t just for storing data. It is a true transactional engine built for accuracy, consistency, and reliability.
Unlike MySQL, PostgreSQL supports transactional guarantees for both DML and many DDL operations, so even complex changes can be rolled back safely.

🔹 What Is a Transaction?

A transaction is a logical unit of work that follows the ACID principles:

  • Atomicity: All operations succeed or none do.

  • Consistency: The database remains valid before and after.

  • Isolation: Concurrent transactions don’t interfere.

  • Durability: Once committed, changes survive crashes.

🧩 PostgreSQL vs. MySQL Example

PostgreSQL treats even certain DDL statements as transactional.

BEGIN;
CREATE TABLE t1(id int);
INSERT INTO t1 VALUES (1);
ROLLBACK;  -- Both table and data disappear

In MySQL, creating a table would trigger an auto-commit, so rollback would not undo the table creation.
That’s the first fundamental difference between the two systems.

🔹 Core Transaction Commands

Command Purpose
BEGIN Start a new transaction
COMMIT Make all changes permanent
ROLLBACK Undo all changes since BEGIN

🧩 Using Savepoints

To perform partial rollbacks, PostgreSQL provides SAVEPOINT:

BEGIN;
INSERT INTO orders VALUES (2, 'pending');
SAVEPOINT step1;
UPDATE orders SET status = 'open' WHERE id = 2;
ROLLBACK TO SAVEPOINT step1;  -- Undo update, keep insert
COMMIT;

Savepoints let you recover from errors gracefully without discarding the whole transaction.
MySQL also supports savepoints, but PostgreSQL integrates them seamlessly with transactional DDL, making complex operations much safer.

🔹 Transaction Lifecycle in PostgreSQL

A typical transaction goes through these steps:

  1. BEGIN — Start the transaction.

  2. Execute one or more DML statements.

  3. MVCC & WAL:

    • PostgreSQL uses MVCC (Multi-Version Concurrency Control) for snapshot isolation.

    • Every change is recorded in WAL (Write-Ahead Log) for durability.

  4. COMMIT or ROLLBACK:

    • COMMIT makes all changes permanent.

    • ROLLBACK discards them entirely.

🔹 Transaction Isolation Levels

PostgreSQL provides four isolation levels:

Level Description
Read Uncommitted Treated as Read Committed
Read Committed (default) Sees only committed changes
Repeatable Read Provides consistent snapshots
Serializable Strictest; detects conflicts and may abort transactions

🔹 Transactional DDL

One of PostgreSQL’s strengths is that many DDL operations are transactional:

Transactional DDL examples:

  • CREATE TABLE
  • ALTER TABLE
  • DROP TABLE
  • CREATE INDEX
  • DROP INDEX
  • CREATE FUNCTION
  • GRANT / REVOKE

Non-transactional exceptions:

  • CREATE DATABASE
  • DROP DATABASE
  • CREATE TABLESPACE
  • CLUSTER
  • VACUUM FULL
  • ALTER SYSTEM

🧩 Example

BEGIN;
CREATE TABLE test(id int);
INSERT INTO test VALUES (1);
ROLLBACK;  -- table disappears

Benefits:

  1. Consistency: prevents half-created tables or indexes.

  2. Catalog integrity: all system catalog updates are transactional.

  3. Flexibility: enables safe schema + data migrations together.

MySQL, in contrast, auto-commits DDL, which makes mixed DDL and DML operations unsafe.

🔹 Long Transactions: Hidden Dangers

Long-running transactions can cause:

  • Accumulated dead tuples, leading to table bloat.

  • Autovacuum delays, since old rows might not be reclaimed.

  • Transaction ID wraparound risks.

Best Practices:

  • Keep transactions short.

  • Split large updates into smaller batches.

  • Monitor long-running sessions in pg_stat_activity.

🔹 Combining DDL and DML Safely

PostgreSQL allows mixing both reliably:

BEGIN;
ALTER TABLE orders ADD COLUMN status text;
UPDATE orders SET status = 'open';
COMMIT;

If the UPDATE fails, the schema change is also rolled back automatically, something impossible in MySQL.

For users coming from MySQL, this transactional behavior means you can refactor tables and initialize data safely without risking partial changes or inconsistent states.

🔹 Common Misunderstanding: Statement-Level Errors

MySQL Example

CREATE TABLE tx(id INT PRIMARY KEY, name VARCHAR(20));
BEGIN;
INSERT INTO tx VALUES(1, 'foo');
INSERT INTO tx VALUES(1, 'bar');  -- Duplicate key
COMMIT;

  • The first insert succeeds.

  • The second fails.

  • Transaction still commits the first insert.

PostgreSQL Example

BEGIN;
INSERT INTO tx VALUES(1, 'foo');
INSERT INTO tx VALUES(1, 'bar');  -- Duplicate key error
COMMIT;  -- Entire transaction is rolled back, first insert undone

  • A single failed statement aborts the entire transaction.

  • Nothing remains after rollback.

This is a simplified sequence diagram, for the sake of simplicity.

From the sequence diagram above, we can see that:

  1. Even if the user executes COMMIT, the server returns a ROLLBACK because the transaction was already marked as failed.

  2. Once an error occurs, PostgreSQL immediately performs an abort transaction, writing an abort record to WAL for crash safety.

  3. The duplicate check happens during the index insertion process.

  4. PostgreSQL does not physically undo the changes; it simply marks the transaction as aborted. MVCC then hides these tuples from all other transactions.

  5. The duplicate tuple still exists in the heap but is invisible. Later, VACUUM reclaims the space by checking its transaction status.

This is very different from MySQL, which prevents duplicates before inserting into the clustered index. PostgreSQL writes first and hides later; MySQL checks first and never writes.

🔹 Error Handling: PostgreSQL vs. MySQL

Both PostgreSQL and MySQL guarantee transaction atomicity (all-or-nothing), but they handle mid-transaction errors differently:

  • PostgreSQL – Stops on Error
    Any error immediately aborts the entire transaction.

  • MySQL – Normally Rolls Back the Statement
    A failing DML statement is rolled back, but the transaction may continue depending on the error type.

    Caution: However, committing the transaction after such an error often becomes impossible, leaving it in a "doomed" state that requires a manual rollback.

🔹 Key Differences: PostgreSQL vs MySQL

Feature PostgreSQL MySQL (InnoDB)
DDL transactional ✅ Yes (with some exceptions) ❌ auto-commit
DML transactional ✅ Yes ✅ Yes
Savepoints ✅ Yes ✅ Yes
Long transaction impact Dead tuples, autovacuum Undo log growth
Mix DDL + DML ✅ Generally safe ❌ Unsafe

✅ Summary

PostgreSQL’s transaction system is an almost complete consistency framework, covering both schema and data. It supports transactional DDL (with some exceptions), savepoints, and WAL-based durability, which enables

  • safer migrations

  • stronger atomicity

  • easier rollback

  • reliable concurrency
