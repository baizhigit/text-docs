🌳 Join Tree Structures in Query Optimization

Explore how PostgreSQL arranges joins across multiple tables into tree structures, the different types of join trees, and how these trees determine the sequence of join operations.

💡 1. Why Join Trees Matter

When you write a SQL query involving multiple table joins, the database has many possible ways to execute it, and the order of joins can greatly impact performance.

  • These possibilities are represented as join trees, which show different ways tables can be combined.

  • The planner explores these trees to find the lowest-cost execution plan.

Understanding join trees helps developers:

  • See why certain indexes or join methods are chosen.

  • Optimize queries by restructuring joins or adding appropriate indexes.

  • Understand the database’s limitations. For example, MySQL only supports left-deep trees, which explains why its performance may lag behind PostgreSQL in complex join scenarios.

📐 2. What a Join Tree Is

A join tree is a hierarchical representation of tables and joins in a query:

  • Leaf nodes represent base tables.

  • Internal nodes represent join operations (e.g., nested loop, hash join, merge join).

  • Root node represents the final join result.

Example Query:

SELECT *
FROM orders o
JOIN customers c ON o.customer_id = c.id
JOIN products p ON o.product_id = p.id;

Examples of possible join trees:

  • (orders JOIN customers) JOIN products

  • (orders JOIN products) JOIN customers

  • (customers JOIN products) JOIN orders

Each tree corresponds to a different execution order.

🌳 3. Join Tree Structures

In the previous lesson, we covered three basic join tree structures. Let’s take a quick moment to review them here.

3.1 Left-Deep Tree

This is the simplest join tree structure. Its main characteristic is that the result of each join is always joined with a base table. The MySQL community version uses this structure, and its entire join processing follows a left-deep tree architecture.

3.2 Right-Deep Tree

Right-deep trees reverse the join order. They are less common but can be useful in certain pipelined execution scenarios.

3.3 Bushy Tree

When handling joins, PostgreSQL also considers bushy trees. This allows the planner to explore more execution plans and increases the chances of finding an efficient one.

⚡4. Join Methods and Their Suitability by Join Tree

Different join trees favor different join methods. Understanding this helps explain planner choices and performance implications.

4.1 Left-Deep Tree

  • Structure: Joins form a linear chain; the right input of each join is always a base table.

  • Join Method Analysis:

    • Nested Loop Join: Usually highly efficient; the inner table is a base table, often indexed, allowing efficient probing.

    • Merge Join: Suitable if inputs are pre-sorted or indexed; otherwise, additional sorting is needed.

    • Hash Join: Possible if the inner table is small enough to fit in memory, but less common due to linear chaining.

  • Notes: Supports pipelined execution efficiently, minimizing materialization of intermediate results.

4.2 Right-Deep Tree

  • Structure: Joins chain from right to left; the left input of each join is always a base table.

  • Join Method Analysis:

    • Nested Loop Join: Works if the input is small, but usually inefficient because the right side can produce large unindexed intermediate results.

    • Hash Join: Generally effective, and able to handle large intermediate results well as long as the corresponding hash tables fit in memory.

    • Merge Join: Works if both inputs are sorted, though extra sorting may be required.

4.3 Bushy Tree

  • Structure: Joins can be performed in any order; both sides can be complex subtrees.

  • Join Method Analysis:

    • Hash Join: Highly suitable; both sides may be intermediate results, and hash probing remains efficient.

    • Merge Join: Suitable if inputs are sorted; may require additional sorting.

    • Nested Loop Join: Usually inefficient for large intermediate results, but possible for small inputs.

  • Notes: Explores more join combinations, increasing the search space but potentially reducing execution cost for complex queries.

The planner appears to mix left-deep and right-deep join trees, with a total estimated cost of 92,271.91. From the comparison, we can see that letting the planner consider bushy trees reduces the estimated cost to 89,025.98, showing that bushy plans can lead to better performance.

Let’s look at the join tree when bushy plans are disabled. The diagram below shows a combination of left-deep and right-deep trees in PostgreSQL. PostgreSQL does not strictly follow left-deep or right-deep structures. When the root node joins its two child nodes, the products table and an intermediate hash join result, two possible join orders can be considered:

  1. products joined with the intermediate hash join result

  2. The intermediate hash join result joined with products

Ultimately, PostgreSQL selects the second join order, joining the intermediate hash join result with products. This demonstrates that PostgreSQL is not limited to left-deep or right-deep tree structures.

🎯 6. Practical Implications for Developers

  1. Query restructuring: Rewriting joins in a different order may help the planner explore more efficient paths.

  2. Indexing: Proper indexes reduce scan costs and make certain join trees more favorable.

  3. Analyze tables: Keeping table statistics up to date improves cost estimation and join tree selection.

For complex join queries, breaking the query into smaller subqueries may reduce the search space and help the planner make better decisions.

With this classification, we can track how many left-deep, right-deep, and bushy join trees the planner considers when evaluating paths for a given join query.

Let's use the same SQL as an example.

SELECT
    c.id AS customer_id,
    c.name AS customer_name,
    o.id AS order_id,
    p.id AS product_id,
    p.name AS product_name,

For the join above, which involves only four tables, we tracked the types of sub-joins considered during path analysis:

  • Bushy trees: 0

  • Left-deep trees: 104

  • Right-deep trees: 76

What happens when we increase the number of tables? Let’s examine a join involving 16 tables to see how the statistics change.

SELECT c.custkey, c.name, n.name AS nation, r.name AS region,
       o.orderkey, o.orderdate, l.partkey, p.name AS part_name,
       pc.name AS category, s.name AS supplier_name, sh.ship_date,
       car.name AS carrier, w.location AS warehouse, d.name AS dept,
       e.name AS employee, pr.discount, tx.amount
FROM customers c
JOIN orders o      ON c.custkey = o.custkey
JOIN lineitems l   ON o.orderkey = l.orderkey
JOIN parts p       ON l.partkey = p.partkey
JOIN part_categories pc ON p.category_id = pc.category_id
JOIN suppliers s   ON l.suppkey = s.suppkey
JOIN shipments sh  ON l.ship_id = sh.ship_id
JOIN carriers car  ON sh.carrier_id = car.carrier_id
JOIN warehouses w  ON l.warehouse_id = w.warehouse_id
JOIN nation n      ON c.nationkey = n.nationkey
JOIN region r      ON n.regionkey = r.regionkey
JOIN accounts a    ON c.custkey = a.custkey
JOIN transactions tx ON a.account_id = tx.account_id
JOIN promotions pr ON p.partkey = pr.partkey
JOIN employees e   ON e.emp_id = (l.lineitem_id % 5000) + 1
JOIN departments d ON e.dept_id = d.dept_id
WHERE r.name = 'ASIA'
  AND p.type = 'STEEL'
  AND o.orderdate BETWEEN DATE '2024-01-01' AND DATE '2024-12-31';

  • Bushy trees: 219,339

  • Left-sided trees: 275,876

  • Right-sided trees: 92,849

As the number of joined tables increases, the planner is more likely to generate bushy trees for sub-joins. Bushy trees depend heavily on hash joins, which may explain why MySQL often falls behind PostgreSQL when handling complex joins.

🔑 8. Summary

  • Different join tree types and join methods correspond closely to underlying data structures and algorithms.

  • For the planner, it needs to fully explore every type of join tree to avoid missing potentially better execution plans.

  • Understanding join trees helps developers see why PostgreSQL is so powerful and why MySQL’s join performance can be much lower
