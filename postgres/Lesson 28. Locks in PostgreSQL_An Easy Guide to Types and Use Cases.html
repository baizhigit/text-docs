🔐 Locks in PostgreSQL: An Easy Guide to Types and Use Cases

Locks keep your data consistent and safe when many sessions access it at the same time. Understanding them helps you write faster and safer SQL.

PostgreSQL relies on MVCC (Multi-Version Concurrency Control) and a powerful lock manager to coordinate concurrent access.
While MVCC eliminates many conflicts between readers and writers, locks are still essential for operations that modify data or schema structures.

In this lesson, you’ll learn:

  • The types of locks PostgreSQL provides

  • How PostgreSQL manages locks internally

  • When and why locks matter in real-world queries

  • How PostgreSQL’s design compares with MySQL

🔑 What Is a Lock?

A lock is a control mechanism that prevents other sessions from performing actions that would conflict with your transaction.

PostgreSQL supports several levels of locking:

  • Row-level locks – lock only specific tuples (rows) to maximize concurrency

  • Table-level locks – lock an entire table to protect structure or bulk changes

  • Advisory locks – application-defined locks for business logic synchronization

  • Predicate locks – used internally to prevent phantom reads under SERIALIZABLE isolation

💡 MVCC advantage:
In most cases, readers don’t block writers, and writers don’t block readers.
Locks are mainly needed for DDL, concurrent updates, and integrity guarantees.

🔍 Two Locking Mechanisms in PostgreSQL

When a statement executes, PostgreSQL may acquire two kinds of locks, depending on what it touches.

1️⃣ Lock Manager Locks (In-Memory)

For objects like tables, transactions, or advisory keys:

  1. PostgreSQL determines which resource needs protection.

  2. It registers a lock request in the Lock Manager (shared memory).

  3. The Lock Manager checks for conflicts and may put the process into a wait queue.

  4. Once granted, the lock appears in the system view pg_locks.

SELECT pid, locktype, relation::regclass, mode, granted FROM pg_locks;

These locks are temporary; they disappear after a crash or restart.

2️⃣ Tuple Locks (On-Disk Metadata)

For row-level locks such as SELECT … FOR UPDATE:

  • PostgreSQL does not allocate a separate lock object in memory.

  • Instead, it updates the tuple’s XMAX with the current transaction ID (XID).

  • This marks the row as “locked by” that transaction.

  • The change is written to WAL, so recovery knows which rows were being modified.

Tuple locks therefore rely on visibility rules rather than the Lock Manager. They are part of the MVCC system and ensure consistent reads and writes at the row level.

🔧 Locks vs. Latches

Locks Latches (Lightweight Locks)
Manage transaction-level concurrency Protect low-level shared memory
Ensure logical data consistency Ensure in-memory structure integrity
Visible in pg_locks Not visible via SQL
Higher-level abstraction Lower-level performance mechanism

⚠️ Remember:
Locks protect data consistency. Latches protect internal memory consistency. Both can affect performance, but at very different levels.

🧱 Common Lock Types in PostgreSQL

Row-Level Locks

  • Acquired by statements that modify or lock specific rows, such as UPDATE, DELETE, or SELECT … FOR UPDATE.

  • Affect only those tuples, not the whole table.

  • Four modes:

    • FOR UPDATE – exclusive row lock

    • FOR NO KEY UPDATE

    • FOR SHARE

    • FOR KEY SHARE

These locks still generate WAL entries, since changing XMAX modifies the tuple header. So, conceptually, SELECT … FOR UPDATE is also a kind of write operation.

Table-Level Locks

Automatically acquired for DDL and DML operations:

Command Lock Mode Description
SELECT ACCESS SHARE Normal read
SELECT … FOR UPDATE ROW SHARE Protects selected rows
INSERT/UPDATE/DELETE ROW EXCLUSIVE Standard write operations
CREATE INDEX SHARE Prevents writes during index creation
ALTER TABLE EXCLUSIVE Schema modification
DROP TABLE, VACUUM FULL ACCESS EXCLUSIVE Full lock, blocks everything

Conflicting modes must wait until others are released.

Advisory Locks

  • User-defined locks, independent of tables or rows.

  • Managed explicitly using:

SELECT pg_advisory_lock(1);
SELECT pg_advisory_unlock(1);

or transaction-scoped:

SELECT pg_advisory_xact_lock(1);

They’re great for business-level synchronization, such as preventing concurrent updates on the same customer record.

Predicate Locks

PostgreSQL uses predicate locks under the SERIALIZABLE isolation level to prevent phantom reads without relying on gap locks. These locks are stored in shared memory and represent logical conditions rather than physical rows or gaps.

If a concurrent transaction would violate serializability, PostgreSQL automatically aborts it.

This approach is more robust and less intrusive than MySQL’s gap-lock mechanism, providing strong consistency with minimal contention.

🔄 Deadlocks and MVCC

PostgreSQL automatically detects deadlocks. When two sessions wait on each other, it aborts one session to break the cycle.

MVCC reduces deadlock frequency because:

  • Readers don’t block writers.

  • Writers often work on different tuple versions rather than shared ones.

🧪 Practical Examples

Example 1: Locking a Single Row

BEGIN;
SELECT * FROM users WHERE id = 50 FOR UPDATE;

This locks the row with id = 50. Any other transaction attempting to modify or delete this row must wait.

Internally, PostgreSQL stores the row-level lock in the tuple’s XMAX field.

Example 2: Table-Level Lock Conflict

BEGIN;
ALTER TABLE users ADD COLUMN note TEXT;

This acquires an ACCESS EXCLUSIVE lock, blocking all concurrent queries on users until it finishes.

Example 3: Classic Deadlock

Step Session A Session B
1 begin; begin;
2 update users set name='Alice' where id = 1; update users set name='Blob' where id = 2;
3
4 update users set name='James' where id = 2;
5 update users set name='alice' where id = 1;
6

As shown in the diagram above, we can see that:

  • Session A tries to update id = 2 and waits for Session B.

  • Session B tries to update id = 1 and waits for Session A.

  • PostgreSQL detects a deadlock cycle and automatically aborts one of the transactions.

Example 4: Advisory Lock for Serialized Access

You can use an advisory lock to ensure that updates for each user are processed one at a time, so sessions execute them serially.

Here is an example of an advisory lock:

-- Session A
BEGIN;
SELECT pg_advisory_xact_lock(1); -- Lock user_id=1
-- Session B
BEGIN;
SELECT pg_advisory_xact_lock(1); -- Waits for Session 1

Here, an advisory lock ensures that only one session can proceed at a time.

🧩 How PostgreSQL Differs from MySQL

Feature PostgreSQL MySQL (InnoDB)
Row locks stored In tuple header (XMAX) In lock hash table
Gap locks ❌ None (uses predicate locks instead) ✅ Used in REPEATABLE READ
Predicate locks ✅ Implemented for SERIALIZABLE (SSI) ❌ Not available
Advisory locks ✅ Built-in, flexible ⚠️ Limited via GET_LOCK/RELEASE_LOCK

PostgreSQL’s design is powerful: row locks are integrated into MVCC, not managed by an external system.

🧠 Performance Implications

When locks cover too many rows or tables, you may face:

  • ⛔ High memory usage in the lock table

  • ⛔ Increased deadlock risk

  • ⛔ Long blocking chains

✅ Keep transactions short and specific.

The shorter the lock duration, the healthier your concurrency.

📌 Key Takeaways

  • PostgreSQL uses row locks integrated with MVCC, rather than a separate locking system.

  • Row-level and table-level locks ensure consistency during updates.

  • Advisory locks provide flexible, application-level control, but they must be managed explicitly by the developer.

  • Predicate locks enforce serializable isolation safely and efficiently, but only apply under the SERIALIZABLE isolation level.

  • Keep transactions short to minimize blocking and contention.

🧠 Mastering PostgreSQL locks helps you build high-performance, deadlock-free, and logically consistent systems, as long as you understand their scope and limitations.
